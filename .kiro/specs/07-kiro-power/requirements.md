# Requirements Document

## Introduction
**HexCard Kiro Power: validate, compile, conjure, draw and preview HexCard stacks from a Kiro chat.**

**Basis.** The expected install and start behaviour of the power comes only from finding K1: the public Kiro documentation and the Agent Plugins 1.0.0 specification. Where a requirement needs a behaviour of Kiro that K1 does not state, the requirement states it as an expectation. No live import has been made for this spec. The live import is the first step of the real-use requirement (Requirement 16.1). It confirms or corrects every expectation, and that task records the result in this paragraph and in the findings (Requirement 16.2). The Kiro power findings are K1 and K3, below. The text rendering finding follows them.

This spec adds a Kiro power named `hexcard` in the folder `powers/hexcard/`. It gives a Kiro chat five MCP tools that run HexCard's own code, and two skills that teach the chat to build stacks and write HexTalk. The tools are `validate_stack`, `compile_hextalk`, `conjure_script`, `render_card` and `draw_layer`. The last task first confirms the live import, then uses the power in a real Kiro chat to build a new showcase stack.

The spec adds no persisted field and changes neither schema 2.0.0 nor the HexTalk grammar. It reuses what exists:
- spec 01: `validateStack` (`src/core/stackValidator.ts`), the load gate of spec 01 Requirement 6;
- spec 02: `parseHexTalk` and `printHexTalk` (`src/core/parser.ts`) and their round-trip guarantees;
- spec 03: `encodeBitmapRLE` / `decodeBitmapRLE`, `composeFrame`, `createPartRasterizer`, `renderCrisp1BitText` with its `TextRasterBackend` adapter, `FONT_FILES` and `TEXT_SIZE_TABLE`; the 38 `PATTERNS` and `patternState` (`src/engine/graphics/patterns.ts`); `bresenhamLine` and the Rect and Line tools (`src/engine/graphics/paintTools.ts`);
- spec 04: `checkStack` (`src/storage/stackLoader.ts`), `decodeStackPayload` and `encodeStackFile` (`src/storage/stackFile.ts`), the Tier 1 Spellcaster `conjureLocally` and `handlerHint` (`src/ai/spellcaster.ts`), and the showcase stacks of `src/presets/index.ts`;
- spec 06: button icons from `customIcons`, drawn by the part renderer.

Canonical contracts: schema `hexcard_design_spec.md` §2.1, concurrency model §3.2, grammar §4.1, AST and parser contract §4.2, VM semantics §4.3, Spellcaster acceptance pipeline §4.4, patterns §5.3, bitmap codec §5.4, text pipeline §5.5, composition §5.6.

**Kiro power findings.** Sources read on 2026-11-10:
- K1, public documentation and specifications. These sources are the only basis for what this spec expects Kiro to do when it imports and starts the power:
  - [Powers](https://kiro.dev/docs/powers/) and [Create powers](https://kiro.dev/docs/powers/create/): powers follow the Agent Plugins format. A power is a folder with a required `plugin.json` and the optional `skills/` (one folder with a `SKILL.md` file for each skill) and `mcp.json`. Kiro's minimum manifest has `$schema`, `name`, `version`, `description`, `author` (an object with at least `name`) and `keywords`; `homepage`, `repository` and `license` are optional. Kiro uses `name` to identify the power, and activates the power when a conversation uses one of its keywords. A power can sit in a folder of a repository, and one repository can hold several powers, each in its own folder. During installation Kiro namespaces the names of the power's MCP servers to avoid conflicts. The page gives one example and no rule: the server `supabase-local` of a power whose `name` is `supabase`, shown in a folder named `power-supabase`, becomes `power-supabase-supabase-local`. That example fits more than one rule (`power-`, the `name`, `-` and the server name; or the folder name, `-` and the server name), so this spec does not derive the name of this power's server from it.
  - [Install powers](https://kiro.dev/docs/powers/installation/): Powers panel, Add Custom Power, then Import power from a folder (choose the folder that holds `plugin.json`) or Import power from GitHub (enter a repository URL). Each power needs a valid `plugin.json` or `POWER.md` at its root. Kiro still reads the legacy `POWER.md` format, which this spec does not use. For a power in the Agent Plugins format, Kiro manages the MCP servers itself, outside `~/.kiro/settings/mcp.json`, and starts and stops them with the power. A local MCP server runs with the user's access unless it is sandboxed, so it can run code and read the user's files; Requirement 2.3 sandboxes this power's server with Node's permission model. The page does not say where Kiro keeps an imported power, or whether Kiro runs the power from the chosen folder or from a copy of it.
  - [MCP](https://kiro.dev/docs/mcp/) and [MCP tools](https://kiro.dev/docs/mcp/usage/): Kiro leaves out a tool whose description is empty, whose name does not match `^[a-zA-Z][a-zA-Z0-9_]*$`, or whose name with the server prefix is longer than 64 characters, and it warns about a tool description longer than 10,000 characters. The MCP servers tab of the Kiro panel shows each server's connection status and tools, and the output channel "Kiro - MCP Logs" shows the servers' errors. No page read for this spec says whether the chat model is shown the image content of a tool result.
  - [Agent Plugins specification 1.0.0](https://agent-plugins.org/specification): a plugin is a self-contained folder, and the plugin root is the top-level folder of the plugin (§3). A client rejects a package path that resolves outside the plugin root; a symbolic link may point inside it (§4.1). `plugin.json` has a closed field set, `$schema`, `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords` and `extensions`, and a client reports and ignores any other field (§5.2). `author` may hold only `name`, `email` and `url` (§5.4). Each direct subfolder of `skills/` that holds a `SKILL.md` file is one skill (§7.1). The MCP specification defines the wire protocol and the session lifecycle (§7.2). `mcp.json` holds only `$schema` and `mcpServers`, and a stdio server entry holds only `type`, `command`, `args`, `env` and `cwd` (§7.2.1). A stdio `command` is one token: either a bare name, which the client resolves with the platform's executable search, or a `./` path resolved against the plugin root. The client expands no placeholder in `command`, and an omitted `cwd` means the plugin root (§7.2.1). A server that fails to start or to finish the MCP handshake does not stop the plugin's other components, and the client should report the failure (§7.2.2). The client sets two variables in the server's environment: `PLUGIN_ROOT`, the absolute path of the plugin root, and `PLUGIN_DATA`, the absolute path of a writable data folder that the client creates before the start. Apart from the executable search for a bare command, a conforming plugin depends on no other variable of the inherited environment (§9.1). The client replaces every exact occurrence of `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` as text, in one pass that does not scan the replaced text again, in every `args` element, every `env` value and `cwd`, and leaves any other placeholder-like text literal (§9.2). The `$schema` versions of `mcp.json` and `plugin.json` must match (§10.1).
  - [Agent Skills specification](https://agentskills.io/specification) and Kiro's [Agent Skills](https://kiro.dev/docs/skills/) page: a skill's `name` must match its folder and has 1 to 64 characters, all lowercase letters, digits and hyphens, with no hyphen at either end and no two hyphens in a row. Its `description` has 1 to 1,024 characters.
- K3, local Node check, outside Kiro. A throw-away server (not part of the repository) was started by hand on Node 24.19.0 with the start line of Requirement 2.3, the placeholder already replaced: `node --permission --allow-fs-read=<server file> --disallow-code-generation-from-strings <server file>`. The server answered. Node's permission model allowed reading the server file. It refused reading other files, writing, child processes and worker threads, and `new Function` threw. It did not stop a network request: `fetch` reached DNS, because Node 24's permission model has no network scope. Which releases accept the option `--permission` comes from Node's release notes and documentation, not from a local run. Node.js 23.5.0 made the permission model stable and replaced `--experimental-permission` with `--permission` ([23.5.0 release notes](https://nodejs.org/en/blog/release/v23.5.0), "src,lib: stabilize permission model"). Node.js 22.13.0 made the same change on the 22 line ([22.13.0 release notes](https://nodejs.org/en/blog/release/v22.13.0)). Node.js 23.0 to 23.4 still document only `--experimental-permission` ([23.3.0 permissions documentation](https://nodejs.org/docs/v23.3.0/api/permissions.html)), so they do not accept the start line. The power therefore needs Node.js 22.13 or later, except 23.0 to 23.4. Kiro's own start of the server is first seen in the live import (Requirement 16.1).

**Text rendering finding.** In the studio, card text goes through `createCanvasTextBackend`: `fillText` on an OffscreenCanvas, then `alpha >= 128`. Node has no canvas and no `FontFace`, so `render_card` needs another `TextRasterBackend`. Measurements made for this spec:
- fontTools on the nine files in `public/fonts/`: none has a hinting program (`fpgm`), kerning (`kern` or `GPOS`) or a default-on substitution. Fairfax Serif's `GSUB` has only `fwid` and `ss20`, which are off by default. Every glyph is built from straight lines. Every outline point lies on the 100-units-per-pixel grid, except 9 points in 7 glyphs (in 6 of the files) that are 2 to 4 units off (0.02 to 0.04 px). Every mapped character's advance is a whole number of pixels. Every font maps all of printable ASCII (U+0020 to U+007E). The Pixel Operator files map 238 code points each and Fairfax Serif maps 356.
- Headless Chrome 157 (`--headless=new --disable-lcd-text`) drew every mapped character from U+0020 up, without C1 controls, of every font at both render sizes `TEXT_SIZE_TABLE` uses. Each was drawn alone, in 24-character runs and in a pangram: 4,728 cases, the way the canvas backend draws, at an integer `x` and baseline. Chrome produced no partly transparent pixel. A separate rasterizer of the TrueType outlines (nonzero winding, one sample at each pixel centre, pen moved by the `hmtx` advance) gave the same thresholded pixels in 4,724 cases. The other 4 contain U+00AD, which Chrome draws as nothing with no advance.
- A second Chrome run showed that U+00AD and U+200B are drawn as nothing with no advance in both a Pixel Operator and the Fairfax face. U+0009, U+000B and U+000C are drawn as a space. An unmapped character (U+2603) is drawn with a fallback system font at a fractional advance (14.34 px at 16 px), which no renderer can reproduce without that system font.
- `measureText` returned up to 1/65536 px per glyph less than the sum of the advances, and never more. The text layout uses widths only through `Math.ceil`, `Math.round` and comparisons with integer widths, so exact sums give the same layout for lines of fewer than 65,536 characters.
- Result: pixel-identical text is achievable in Node without native modules for covered characters (Glossary). It was measured only in Chrome 157 on Linux. Firefox, Safari, macOS and Windows were not measured. Uncovered characters cannot match and are reported instead (Requirement 10.5).

Out of scope: publishing the power to npm or to the Kiro powers registry; the Spellcaster's Tier 2 proxy and Tier 3 BYOK; any change to the studio UI except what the new showcase stack needs; tools that change a stack, run scripts or play sounds; tools that read or write files or URLs; `draw_layer` shapes other than rectangles, lines, sprites and text (no ovals, curves, brushes, flood fill or image import), and drawing over existing `rleData`; the Streamable HTTP and SSE transports; MCP resources, prompts, sampling and elicitation; steering files inside the power; checking the power in agent clients other than Kiro IDE, and on macOS or Windows.

## Glossary
Terms of specs 01 to 06 keep their meaning. This spec adds:
- **Power:** the folder `powers/hexcard/` in the Agent Plugins 1.0.0 format (K1).
- **Kiro:** Kiro IDE on Linux. The version used is the one that the live import records (Requirement 16.1).
- **Live import:** the first import of the power into a running Kiro, made in the real-use task (Requirement 16.1).
- **Developer:** the person who carries out this spec's tasks, including the Kiro chat of Requirement 16.
- **Ticked:** a task of this spec's `tasks.md` is ticked when its checkbox is marked done (`[x]`).
- **Task report:** the report that ends a task (workflow rules 2 and 5): the summary lines of `npx tsc -b` and `npx vitest --run`, what was done, and the section "Decisions for review".
- **Plugin root:** the folder the client runs the power from, which Agent Plugins 1.0.0 calls the plugin root and `mcp.json` names `${PLUGIN_ROOT}` (K1, §3 and §9). The client passes its absolute path to the server as the environment variable `PLUGIN_ROOT` (§9.1). For Kiro, the live import records where this folder is and whether it is the imported folder or a copy of it (Requirement 16.1).
- **Server:** the power's stdio MCP server. **Server file:** the one committed JavaScript file that is the server. **Build script:** the committed script that produces the server file from the repository's sources.
- **Tool:** one of `validate_stack`, `compile_hextalk`, `conjure_script`, `render_card` and `draw_layer`.
- **Result:** the answer to one `tools/call` that is not a JSON-RPC error. Its `content` starts with exactly one text content, whose text is the result's JSON text: a JSON object with an `ok` field for the tool's verdict. The only other content a result can have is the image content that a `render_card` result with `ok` true adds after the text content (Requirement 9.4). An **error result** is a result whose MCP `isError` is true: the arguments were invalid, the input could not be read, or the tool failed. The JSON text of an error result has `ok` false and an `errors` field, a list of strings with one entry for each error. The read errors of Requirement 6.2, the `render_card` errors of Requirements 9.1 and 9.2 and the internal error of Requirement 4.10 are error results in this form.
- **Canonical form:** the text that `printHexTalk` returns for the AST that `parseHexTalk` returns for a script with no compile error (Requirement 7.3).
- **Tool product:** a text that a tool returns as its output and that Requirement 5.7 returns whole: the canonical form (Requirement 7.3), the handler names (Requirements 7.2 and 7.3), the HexTalk of an accepted spell (Requirement 8.2), the `.hexstack` text (Requirement 6.6) and the `rleData` (Requirement 11.7). Every other text of a result is a **message** (Requirement 5.7).
- **Characters:** in a limit, a length or a count, UTF-16 code units, as JavaScript's `String.prototype.length` counts them.
- **Stack text:** the `stack` argument. It is either the JSON text of a stack or `.hexstack` text (spec 04 Requirement 5.2).
- **Gate:** `checkStack` in `src/storage/stackLoader.ts`, the studio's load check. It runs `validateStack`, then `decodeBitmapRLE` on every bitmap layer (spec 04 Requirement 5.5). A **gate error** is written `<path>: <message>`, with the path format of `validateStack`.
- **Canonical rleData:** `rleData` equal to `encodeBitmapRLE(decodeBitmapRLE(rleData))`; `""` is the canonical empty layer.
- **Frame:** the 512 x 342 states (1 = light, 2 = dark) that `composeFrame` returns. **Studio frame:** the pixels the studio's card canvas shows.
- **Face:** the font file and render size that `TEXT_SIZE_TABLE` selects for a text's logical font, size and bold style. Button titles use `System` 12 (`BUTTON_TEXT`).
- **Covered character:** for a face, a code point that the face's font file maps in its `cmap`, plus U+0009, U+000B and U+000C (drawn as a space) and U+00AD and U+200B (drawn as nothing with no advance, as Chrome does). Every other code point is an **uncovered character**.
- **Paragraph:** a run of a text between hard line breaks: from the start of the text or a line break (`\r\n`, `\r` or `\n`) to the next line break or the end of the text, as the text layout of `renderCrisp1BitText` splits it.
- **Node text backend:** the `TextRasterBackend` that `render_card` and `draw_layer` use instead of the canvas backend.
- **Layer kind:** the `layer` argument of `draw_layer`, `card` or `background`. **Base:** the 512 x 342 pixels `draw_layer` starts from: every pixel 0 (transparent) for `card` and every pixel 1 (light) for `background`, as `decodeBitmapRLE("")` gives for each layer.
- **Drawing command:** one entry of `draw_layer`'s `commands`, named by its `op` field: a rectangle (`rect`), a line (`line`), a sprite (`sprite`) or a text (`text`). A **sprite** is a list of equal-length rows of `#` (dark) and `.` (light). A **pattern index** is an index from 0 to 37 into `PATTERNS` of `patterns.ts`, where 0 is solid light and 1 is solid dark.
- **Skill:** a folder under `skills/` with a `SKILL.md` file (Agent Skills specification). **Skill example:** an example in a skill file that the test of Requirement 17.4 runs, marked as one of these kinds: a stack example (a fenced code block with the JSON text of a stack), a HexTalk example (a fenced code block with a script), a drawing example (a fenced code block with the arguments of one `draw_layer` call), or a mistake example (a wrong script in a fenced code block with the line, column and message of the error that `compile_hextalk` reports for it, followed by its fixed script as a HexTalk example, Requirement 13.4).

## Requirements

### Requirement 1: Power Package
**User Story:** As a Kiro user, I want to import HexCard's power from the repository in the Powers panel, so that a chat can author HexCard stacks with HexCard's own code.

#### Acceptance Criteria
1. THE SYSTEM SHALL provide the power as the folder `powers/hexcard/` at the repository root, in the Agent Plugins 1.0.0 format. `plugin.json`, `mcp.json` and `skills/` SHALL be at the power's root. `skills/` SHALL hold exactly two skill folders, `author-hexcard-stack` (Requirement 12) and `write-hextalk` (Requirement 13). No file named `POWER.md` SHALL exist anywhere in the power folder.
2. THE SYSTEM SHALL give `plugin.json` exactly these fields and no others: `$schema` set to `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`, `name` set to `hexcard`, `version`, `description`, `author`, `keywords`, `repository` set to `https://github.com/hadbilen/hexcard-resurrection` and `license` set to `MIT`. `author` SHALL be an object whose only field is `name`, set to the copyright holder named in the repository's `LICENSE`. The file SHALL conform to the Agent Plugins 1.0.0 manifest schema, whose field set is closed (K1, §5.2).
3. THE SYSTEM SHALL keep `version` equal, as a string, to the `version` field of the repository's `package.json`.
4. THE SYSTEM SHALL set `keywords` to an array of exactly the four strings `hexcard`, `hextalk`, `hexstack` and `hypercard`, each once and in any order, so that the power activates for HexCard work and not for generic words such as `card` or `stack`.
5. THE SYSTEM SHALL write `description` as one sentence of at most 200 characters, using only printable ASCII (U+0020 to U+007E). Here "one sentence" means that the text ends with `.` and that no `.`, `!` or `?` before the end is followed by a space. Ignoring letter case, the sentence SHALL contain the words `validates`, `compiles`, `conjures`, `draws` and `previews`, the text `HexCard stacks` and the text `Node.js 22.13 or later, except 23.0 to 23.4`.
6. THE SYSTEM SHALL make every entry of the power folder, at every depth, a regular file or a folder, with no symbolic link and no other entry type. THE SYSTEM SHALL keep inside the power folder every file the server reads or imports at run time. Agent Plugins 1.0.0 makes a plugin a self-contained folder and has a client reject package paths that resolve outside the plugin root (K1, §3 and §4.1). K1 does not say whether Kiro runs an imported power from the chosen folder or from a copy of it, so these two rules keep the power working in both cases, whatever a copy or a clone does with symbolic links. THE SYSTEM SHALL also keep every file of the power folder unmatched by the patterns of the repository's `.gitignore`, because Import power from GitHub takes the power from the GitHub repository, which holds only committed files. The `dist/` pattern, for example, matches a folder named `dist` at any depth.
7. THE SYSTEM SHALL include the licence texts below in the power folder. Each text SHALL appear unchanged, character for character, in a file of the power folder, because the power redistributes the repository's code, third-party code and the fonts whose bytes the server file carries (Requirement 3.1):
   - the full text of the repository's `LICENSE` (MIT);
   - for every third-party package whose code the build script puts into the server file (today only Zod), the licence notice of that package, as the licence file of the installed package holds it (for Zod, `node_modules/zod/LICENSE`, the MIT licence with its copyright and permission notice);
   - for the eight Pixel Operator files, the CC0 1.0 legal code, as the text inside its fenced block in `public/fonts/LICENSES.md`;
   - for Fairfax Serif, the OFL-1.1 text with its Kreative Software copyright notice, as the text inside its fenced block in `public/fonts/LICENSES.md`.
8. WHEN the power is imported with Import power from a folder (choosing `powers/hexcard`) or with Import power from GitHub (using the folder URL `https://github.com/hadbilen/hexcard-resurrection/tree/main/powers/hexcard`), THE SYSTEM SHALL be installed under the name `hexcard`. K1 says that Kiro identifies a power by the `name` of `plugin.json`, which is `hexcard` (Requirement 1.2), and the power folder is also named `hexcard`. The power's details in the Powers panel SHALL list the skills `author-hexcard-stack` and `write-hextalk` and the power's MCP server, under the namespaced name that Kiro shows (K1). K1 gives no rule for that name, so no criterion of this spec depends on it, and the live import records it. These are expectations: K1 does not say which name the Powers panel shows for an imported power, nor whether Import power from GitHub takes a URL that points at a folder of a repository. The live import (Requirement 16.1) confirms or corrects them for Import power from a folder, and the GitHub import of Requirement 17.9 checks them for Import power from GitHub.

### Requirement 2: Server Start
**User Story:** As a Kiro user without a HexCard checkout or build tools, I want the power's server to start with only Node installed, so that the tools work right after the import.

#### Acceptance Criteria
1. THE SYSTEM SHALL give `mcp.json` the `$schema` `https://agent-plugins.org/schemas/1.0.0/mcp.schema.json` and exactly one server, named `hexcard`, of type `stdio`. The file `mcp.json` SHALL conform to the Agent Plugins 1.0.0 MCP schema that this `$schema` names.
2. THE SYSTEM SHALL give the server the bare command `node`, no `cwd` and no `env`. It SHALL write the server file in `args` as `${PLUGIN_ROOT}/` followed by the server file's path relative to the power folder, with `/` as the separator, and SHALL use this same text everywhere criterion 3 names the server file. `${PLUGIN_ROOT}` SHALL be the only text of the form `${...}` anywhere in `mcp.json`. Agent Plugins 1.0.0 has a client resolve a bare command with the platform's executable search, replace `${PLUGIN_ROOT}` with the absolute path of the plugin root in every `args` element, and use the plugin root as the working directory when `cwd` is omitted (K1, §7.2.1, §9.1 and §9.2), so the start does not depend on the working directory. That Kiro starts the server this way is an expectation that the live import (Requirement 16.1) confirms or corrects.
3. THE SYSTEM SHALL make `args` exactly these four elements, in this order, as in the start line of K3: `--permission`; `--allow-fs-read=` directly followed by the server file text of criterion 2, with no other path; `--disallow-code-generation-from-strings`; the server file text of criterion 2. With these options Node refuses, in the server process, to read any other file, write any file, start child processes or worker threads, load native add-ons, and run `eval` or `new Function`. K3 saw the file, child process, worker thread and `new Function` refusals. It did not try add-ons or `eval`, which Node documents as refused under these options. Node does not restrict network access (K3), and Requirements 3.2 and 3.3 keep network modules and calls out of the server file. Requirement 17.5 checks this criterion on the `args` values. The refusals are Node's behaviour.
4. THE SYSTEM SHALL make the server run on Node.js 22.13 or later, except 23.0 to 23.4: every 22.x release from 22.13.0 on, and every release from 23.5.0 on. These are the releases that accept `--permission` as a stable option (K3). The server file SHALL use only built-in modules and globals that Node.js 22.13.0 provides with no command-line option other than the three of criterion 3.
5. THE SYSTEM SHALL make the server file's code read no environment variable, and SHALL make it depend neither on the working directory nor on `${PLUGIN_DATA}` or the folder that `${PLUGIN_DATA}` names. The server SHALL then give byte-identical answers to the same requests from any working directory, whether or not `PLUGIN_ROOT` and `PLUGIN_DATA` are set in its environment. Agent Plugins 1.0.0 has the client set both variables in the server's environment (K1, §9.1); the server uses neither.
6. WHEN the power has been imported and the `node` that the platform's executable search finds on the `PATH` of the environment Kiro starts the server with (K1, §7.2.1) is Node.js 22.13 or later, except 23.0 to 23.4, THE SYSTEM SHALL start the server and answer Kiro's `initialize` request (Requirement 4.2). It SHALL do this without `npm install`, without network access and without a build step on the user's machine. The live import (Requirement 16.1) is the first check of this in Kiro.
7. WHEN the server starts, before it reads standard input, THE SYSTEM SHALL check with `process.permission` that the permission model is on, and that it refuses writing files, starting child processes, starting worker threads and reading the folder that contains the server file. The server SHALL find the server file's path from `import.meta.url`, not from the environment or the working directory, so that criterion 5 still holds. IF any of these checks fails (for example because `NODE_OPTIONS` widened the permissions, or `--permission` was left out of the start line), THEN THE SYSTEM SHALL write one diagnostic line to standard error and exit with status 1, without reading standard input and without writing to standard output.

### Requirement 3: Self-Contained Server File
**User Story:** As the maintainer, I want the server shipped as one committed file that is provably built from the current sources and cannot reach files or the network, so that users run exactly the reviewed code.

#### Acceptance Criteria
1. THE SYSTEM SHALL ship the server as one committed JavaScript module in the power folder. The build script SHALL produce it from the repository's TypeScript sources, the installed Zod package and the font files in `public/fonts/`. The server file SHALL contain everything the tools run: the reused HexCard modules, Zod, and the exact bytes of every font file that `TEXT_SIZE_TABLE` selects, identical to the files in `public/fonts/`. The server SHALL need no other file at run time: no second code chunk, no source map, and no separate font or data file.
2. THE SYSTEM SHALL make every static `import` declaration and every `export ... from` declaration in the server file name a Node built-in module. None of them SHALL name `node:fs`, `node:fs/promises`, `node:net`, `node:http`, `node:https`, `node:http2`, `node:tls`, `node:dgram`, `node:dns`, `node:child_process`, `node:worker_threads`, `node:cluster`, `node:vm`, `node:inspector` or `node:module`, the same module without the `node:` prefix (such as `fs`), or a sub-path of one of them (such as `node:dns/promises`). The server file SHALL load modules in no other way: it SHALL contain no call to `require` or `process.getBuiltinModule`, and criterion 3 excludes dynamic `import()`.
3. THE SYSTEM SHALL keep the server file free of references to the globals `fetch`, `WebSocket`, `EventSource` and `XMLHttpRequest`, and free of dynamic `import()` expressions. A reference is either an identifier with one of these names that the file does not declare, or a property with one of these names read from `globalThis`, `global`, `self` or `window`. Text inside string literals and comments does not count, and neither do properties of other objects or longer identifiers that contain these words (such as `fetchJson`). THE SYSTEM SHALL set Zod's `jitless` option to true when the server starts, before the server reads its first message from standard input, so that no tool call makes Zod generate code from strings.
4. WHEN the build script runs more than once on the same sources and the same installed dependencies (the versions `package-lock.json` pins), THE SYSTEM SHALL produce byte-identical server files, whatever the checkout folder, the date and time, the time zone and the user running the script. The server file SHALL therefore contain no absolute file path and no build date or time.
5. IF the committed server file is missing, or differs by at least one byte from the file the build script produces from the sources in the working tree when the test runs, THEN THE SYSTEM SHALL fail a test in `npx vitest --run`, and the failure message SHALL name the npm command of criterion 6 that rebuilds the file (`npm run` followed by the script name). The test SHALL NOT write to the committed server file.
6. THE SYSTEM SHALL provide one npm script in `package.json` that runs the build script and writes the server file to its committed path. THE SYSTEM SHALL leave unchanged the `build` and `build:player` scripts of `package.json`, `vite.player.config.ts` and `.github/workflows/deploy.yml`. `npm run build` SHALL neither run the build script, nor write the server file, nor copy it into `dist/`.
7. WHEN the server file is copied alone into an empty folder outside the repository and started from there with the `args` of Requirement 2.3, with the `--allow-fs-read=` path pointing at the copy, THE SYSTEM SHALL answer `initialize` and `tools/list`, and SHALL return a result that is not an error result for one call of each tool with valid arguments.

### Requirement 4: MCP Protocol
**User Story:** As a Kiro chat, I want the server to follow the MCP stdio protocol strictly and to survive any message, so that one bad request never takes the tools away.

#### Acceptance Criteria
1. THE SYSTEM SHALL implement the MCP stdio transport: JSON-RPC 2.0 messages in UTF-8, one per line, read from standard input and written to standard output. A line is the bytes before an LF (0x0A). A CR before the LF stays part of the line, and JSON reads it as white space. THE SYSTEM SHALL write each message as JSON with no line break inside it, followed by one LF, and SHALL write nothing else to standard output. Diagnostics SHALL go only to standard error and SHALL contain no text read from standard input other than a method name or a tool name.
2. THE SYSTEM SHALL support the protocol versions `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05`. WHEN the server receives `initialize`, THE SYSTEM SHALL answer with the `protocolVersion` the client sent if it is one of these four strings, and with `2025-11-25` otherwise (another version, a value that is not a string, or no `protocolVersion`). This follows the version negotiation of the [MCP specification, revision 2025-11-25, Lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), to which Agent Plugins leaves the protocol (K1, §7.2): a server answers with the version the client requested when it supports that version, and otherwise with another version it supports, preferably its latest. `2025-11-25` is the latest revision this server supports. The version Kiro requests and the version the server answers are recorded in the live import (Requirements 16.1 and 16.2). The answer SHALL declare only the `tools` capability, with `listChanged` absent or false, and SHALL give `serverInfo` the name `hexcard` and the `version` of `plugin.json` (Requirement 1.3). THE SYSTEM SHALL answer a repeated `initialize` by the same rule, and SHALL answer every other message the same way before and after `initialize`.
3. WHEN the server receives `tools/list`, THE SYSTEM SHALL list exactly `validate_stack`, `compile_hextalk`, `conjure_script`, `render_card` and `draw_layer`. Each tool SHALL have a non-empty description and a JSON Schema `inputSchema` of type `object` that:
   - states every argument, and for `draw_layer` every field of every drawing command, with its type, and with its default and its limit (Requirement 5.3) where it has them;
   - marks as required every argument and field that Requirements 6 to 11 neither make optional nor give a default;
   - allows no other argument or field.
   Each tool SHALL carry the annotations `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true` and `openWorldHint: false`.
4. WHEN the server receives `tools/call` for a listed tool whose `arguments` match its `inputSchema` and every limit of Requirement 5.3, THE SYSTEM SHALL run the tool and answer with its result. THE SYSTEM SHALL handle a `tools/call` without `arguments` as one with an empty `arguments` object.
5. IF `tools/call` has no `name`, a `name` that is not a string, or the name of a tool that is not listed, THEN THE SYSTEM SHALL answer with JSON-RPC error -32602. IF the `arguments` do not match the tool's `inputSchema` (`arguments` is not an object, or an argument is missing, unknown, wrongly typed or over its limit), or break a rule of Requirement 5.3 that the `inputSchema` cannot express (Requirement 11.10), THEN THE SYSTEM SHALL answer with an error result, without running the tool. Each entry of its `errors` list SHALL name the path of an argument and the rule that the argument breaks. The path SHALL start with the argument's name, in the form of Requirement 11.10 (for example `stack` or `commands[3].rows[1]`), and SHALL be `arguments` when `arguments` is not an object.
6. WHEN the server receives a `ping` request, THE SYSTEM SHALL answer with an empty result (`{}`). WHEN it receives a notification, whatever its method (for example `notifications/initialized` or `notifications/cancelled`), THE SYSTEM SHALL send nothing. WHEN it receives a request for any other method (for example `resources/list`, `prompts/list` or `logging/setLevel`), THE SYSTEM SHALL answer with JSON-RPC error -32601.
7. IF a line is not valid UTF-8 or not valid JSON, an empty line included, THEN THE SYSTEM SHALL answer with JSON-RPC error -32700 and id `null`. IF a line is valid JSON but not a JSON-RPC 2.0 request or notification, THEN THE SYSTEM SHALL answer with error -32600 and id `null`. A request is a JSON object with `jsonrpc` equal to `"2.0"`, a string `method`, an `id` that is a string or an integer, and either no `params` or an object `params`. A notification is such an object without `id`. A JSON array (a JSON-RPC batch) is neither, whatever protocol version was negotiated, so a batch is answered with -32600 under every supported version. This is a known deviation from protocol revision `2025-03-26`, the only supported revision that allows batches, and affects only a client that negotiates that revision.
8. IF a line grows beyond 33,554,432 bytes (32 MiB) before its LF, THEN THE SYSTEM SHALL discard the line up to and including the next LF, keeping at most 33,554,432 bytes of it in memory, and SHALL answer it once with error -32600 and id `null`. THE SYSTEM SHALL handle a line of 33,554,432 bytes or fewer like any other line. This limit is above the length of every request whose arguments are within Requirement 5.3: a `stack` of 4,194,304 characters takes at most 25,165,824 bytes in a line, when the client writes every character as a six-byte `\uXXXX` escape, so such a request gets an answer with its own `id`.
9. THE SYSTEM SHALL handle lines one at a time, in arrival order, and SHALL write the answer to a line, if it gets one, before it starts handling the next line, so that answers come in the order of the lines they answer. Each answer to a request SHALL carry the request's `id` with the same value and JSON type (`7` stays a number, `"7"` stays a string).
10. IF a tool throws an error that Requirement 5.4 does not cover, THEN THE SYSTEM SHALL answer with an error result whose `errors` list has the single entry `Internal error in <tool>: <message>`, where `<tool>` is the tool's name and `<message>` is the error's `message` (or the thrown value as a string when it is not an `Error`), and SHALL go on handling the next lines. WHILE standard input is open and the start checks of Requirement 2.7 have passed, THE SYSTEM SHALL keep running whatever lines it receives and whatever its tools throw; ending the process with a signal is outside this rule. WHEN standard input ends, THE SYSTEM SHALL answer every complete line received before the end, discard an unfinished last line (the bytes after the last LF) without answering it, and exit with status 0 within 1 second of its last answer.
11. THE SYSTEM SHALL send the client no request (no sampling, roots or elicitation) and no notification (no logging, progress or list-changed notification), so that every line it writes answers a line it received.

### Requirement 5: Untrusted Input and Limits
**User Story:** As a Kiro user, I want the tools to treat every stack, script and drawing command as untrusted and to stay inside fixed limits, so that a hostile or broken input cannot harm my machine or the chat.

#### Acceptance Criteria
1. THE SYSTEM SHALL take every tool input only from the arguments of the `tools/call` request:
   - every argument SHALL be a string, an integer or a boolean, except `commands` of `draw_layer`. That argument is an array of drawing commands. Each command is an object whose fields are strings, integers, booleans or arrays of strings (the `rows` of a sprite and the `style` of a text);
   - no argument SHALL name a file or URL for a tool to open. Text that looks like a path or URL is handled only as text. For example, a `stack` of `https://example.com/a.hexstack` is read as `.hexstack` text and rejected as not valid Base64URL (Requirement 6.2);
   - no tool SHALL read or write a file, open a network connection, start a process or read an environment variable. Requirements 2.3, 2.5, 3.2 and 3.3 enforce this.
2. WHEN `validate_stack` or `render_card` receives `stack`, THE SYSTEM SHALL read the stack text (Requirement 6.1) and check the read value with the gate, the studio's own load check, before any other step of the tool uses the stack:
   - IF the gate rejects the value, THEN the result SHALL hold only the gate errors. It SHALL have none of the additions of Requirement 6.5, and `render_card` SHALL return no image and no card summary (Requirement 9.1);
   - `render_card` SHALL compose a frame only from a stack that the gate accepted in the same call, so it draws only stacks that the studio also loads.

   THE SYSTEM SHALL run no script in any tool, whether the script comes from `source`, from an accepted spell or from a stack. The tools only parse and print scripts (Requirements 7.6 and 9.3).
3. THE SYSTEM SHALL enforce these argument limits. A call that breaks one of them is answered as Requirements 4.5 and 11.10 state, except for the one case given under `stack`. Optional arguments are marked with their defaults. Every other argument is required.
   - `stack` (`validate_stack` and `render_card`): at most 4,194,304 characters. When it is `.hexstack` text, the decompressed JSON is at most 4,194,304 bytes. This number is passed to `decodeStackPayload` as its limit. A stack text over this limit is a read error of `stack` (Requirement 6.2), not an argument error;
   - `hexstack` (`validate_stack`, optional, false when omitted): a boolean;
   - `source` (`compile_hextalk`): at most 65,536 characters;
   - `prompt` (`conjure_script`): at most 600 characters (`MAX_PROMPT_LENGTH` of `spellcaster.ts`);
   - `objectKind` (`conjure_script`, optional, default `button`): one of `button`, `field`, `card`, `background` and `stack`;
   - `card` (`render_card`, optional, default the first card): an integer from 1 to 100,000, or a string of at most 256 characters;
   - `scale` (`render_card`, optional, default 1): the integer 1 or 2;
   - `layer` (`draw_layer`): `card` or `background`;
   - `commands` (`draw_layer`): 1 to 256 drawing commands.
     - Every coordinate (`x`, `y`, `x1`, `y1`, `x2` and `y2`) and every `width` and `height` is an integer.
     - Every point lies inside the 512 x 342 layer: `x`, `x1` and `x2` are from 0 to 511, and `y`, `y1` and `y2` are from 0 to 341.
     - Every rectangle, sprite and text box has a width and height of at least 1 and lies wholly inside the layer: `x + width` is at most 512 and `y + height` is at most 342. A sprite's width is the length of its rows, and its height is the number of its rows;
   - `pattern` of a rectangle or a line: an integer pattern index from 0 to 37;
   - `rows` of a sprite: 1 to 64 rows of the same length, each of 1 to 64 characters, every character `#` or `.`;
   - `text` of a text command: 1 to 256 characters;
   - the sprite rows and texts of one `draw_layer` call: the lengths of every `rows` entry and every `text` value in the call add up to at most 65,536 characters.
4. IF one of these steps throws an exception, THEN THE SYSTEM SHALL answer with an error result that names the argument (`stack`, `source` or `commands`), and SHALL keep serving, which means it answers every later request and does not exit. The steps are the gate, compiling a script (`source`, or a `scriptSource` inside `stack`) and checking the drawing commands. An example of such an exception is a `RangeError` on deeply nested input. An exception thrown while reading the stack text (parsing the JSON text, or `decodeStackPayload`) is a read error of Requirement 6.2 instead. An exception in any other step is an internal error (Requirement 4.10).
5. THE SYSTEM SHALL keep nothing derived from a call's arguments after the call ends. Every tool SHALL therefore return, for the same arguments, the same result that a newly started server returns, whatever calls came before, including calls that ended with an error result. `render_card` SHALL clear the compositor's decoded-layer cache with `clearDecodedLayerCache` at the end of every call, including a call that ends with an error result.
6. IF a list in a result has more than 100 entries, THEN THE SYSTEM SHALL show the first 100 entries in the list's order, followed by the number of entries not shown. This applies to every list of errors (read, gate and compile errors), script errors, notes, parts and uncovered characters. A list of 100 entries or fewer SHALL be shown whole, with no count.
7. THE SYSTEM SHALL put no more than 80 consecutive characters of any argument into a message of a result. Text inside `stack`, such as names, ids, field text and scripts, counts as part of `stack`. A message is every text of a result other than the tool products. WHEN a message quotes a text taken from an argument and that text is longer than 80 characters, THE SYSTEM SHALL quote the text's first 77 characters followed by `...`. A text of 80 characters or fewer SHALL be quoted whole. The tool products SHALL be returned whole: the canonical form (Requirement 7.3), the handler names (Requirements 7.2 and 7.3), the HexTalk of an accepted spell (Requirement 8.2), the `.hexstack` text (Requirement 6.6) and the `rleData` (Requirement 11.7). Every other text that a result takes from an argument is a message and is quoted by this rule, for example the stack name of Requirement 6.5 and the ids, names, titles and field texts of Requirements 9.5 and 9.6.

### Requirement 6: validate_stack
**User Story:** As a Kiro chat building a stack, I want to know whether HexCard would load my stack and, if not, every reason with its path, so that I can fix all problems in one pass.

#### Acceptance Criteria
1. WHEN `validate_stack` receives a `stack` whose first character other than white space is `{`, THE SYSTEM SHALL read it as JSON text: `JSON.parse` of the text without its leading and trailing white space. WHEN it receives any other `stack`, including an empty or all-white-space one, THE SYSTEM SHALL read it as `.hexstack` text: `decodeStackPayload` of the text without its leading and trailing white space, as `decodeStackFile` does, with the decompressed-size limit of Requirement 5.3. In this requirement, white space means the characters that JavaScript's `String.prototype.trim` removes.
2. IF the JSON text is not valid JSON (`JSON.parse` throws a `SyntaxError`), or `decodeStackPayload` rejects the `.hexstack` text because it is not valid Base64URL, deflate-raw, UTF-8 or JSON or because its decompressed JSON is larger than the limit of Requirement 5.3, THEN THE SYSTEM SHALL answer with an error result whose `errors` list has exactly one entry, written as a gate error at path `stack` (`stack: <message>`), and SHALL not run the gate. The message SHALL say which check failed. For `.hexstack` text it SHALL be the message of the error that `decodeStackPayload` throws. Any other throw while reading or checking SHALL be answered as Requirement 5.4 states.
3. WHEN the stack text has been read, THE SYSTEM SHALL check the value with the gate and answer with a normal result (MCP `isError` false). The result SHALL have `ok` true and an empty error list if the gate accepts the value, and `ok` false with the errors of Requirement 6.4 if the gate rejects it.
4. IF the gate rejects the value, THEN THE SYSTEM SHALL return every error the gate finds in one pass, each written as a gate error (for example `cards[1].parts[0].rect.width: expected an integer`), in the order the gate checks them:
   - if the value is a JSON object whose `schemaVersion` is not the string `"2.0.0"`, or that has no `schemaVersion`: that error alone;
   - otherwise, the error for a `__proto__` key in `customIcons` when there is one, then every issue that the schema of `validateStack` reports, in the order it reports them;
   - when the schema reports no issue, whether or not there is a `__proto__` error: every structural error, then every bitmap layer that `decodeBitmapRLE` rejects, background layers before card layers. The structural errors come in this order: for each background, every part whose `layerScope` is not `background`; for each card, a `backgroundId` that names no background, then every part whose `layerScope` is not `card`; every repeated id, once for each occurrence after its first, walking the stack, each background with its parts, then each card with its parts; every button `iconId` that names no key of `customIcons`, the backgrounds' parts before the cards' parts. Backgrounds, cards and parts are always taken in array order.
   The first error SHALL be the error `checkStack` returns, except that every text from `stack` that the error quotes, in its path or its message (such as an id, an icon name or an object key), and that is longer than 80 characters SHALL be shortened as Requirement 5.7 states. A first error that quotes no such text SHALL be exactly the error `checkStack` returns. The list SHALL show at most 100 errors followed by the number not shown (Requirement 5.6). The result SHALL hold no script errors, notes, stack name or counts, and no `.hexstack` text.
5. WHEN the gate accepts the value, THE SYSTEM SHALL also return, without changing `ok` and outside the error list:
   - script errors: every error that `parseHexTalk` reports for every `scriptSource` in the stack, written `<path> line L, column C: <message>`. `<path>` is the gate path of the `scriptSource` (for example `cards[0].parts[2].scriptSource`, or `scriptSource` for the stack's own script), and L and C are 1-based and counted as Requirement 7.2 states. The scripts come in this order: the stack, then each background followed by its parts, then each card followed by its parts, in array order. The errors of one script come in parser order;
   - notes: one note for every bitmap layer whose `rleData` is not canonical, naming the layer's path (for example `backgrounds[0].bitmap.rleData`), background layers before card layers, in array order;
   - the stack's name, quoted as Requirement 5.7 states, its number of cards and its number of backgrounds.
6. WHERE the `hexstack` argument is true, WHEN the gate accepts the value, THE SYSTEM SHALL also return the `.hexstack` text that `encodeStackFile` writes for the stack `checkStack` returns, also when there are script errors or notes. The studio's File > Open Stack File SHALL open this text, and `validate_stack` SHALL return `ok` true for it. The chat can then save the stack for the studio with its own file tools. IF `hexstack` is false or omitted, THEN THE SYSTEM SHALL return no `.hexstack` text.
7. THE SYSTEM SHALL return the same `ok`, errors, script errors, notes, stack name and counts, and `.hexstack` text for a JSON text J and for the `.hexstack` text of J. Here J is any text that `JSON.parse` accepts and whose first character other than white space is `{`; the `.hexstack` text of J is J's UTF-8 bytes compressed with deflate-raw and written as Base64URL without padding (spec 04 Requirement 5.2); and J, its UTF-8 bytes and its `.hexstack` text are within the limits of Requirement 5.3.

### Requirement 7: compile_hextalk
**User Story:** As a Kiro chat writing a script, I want HexCard's parser to check it and give me the canonical text, so that the script I store is exactly what HexCard runs.

#### Acceptance Criteria
1. WHEN `compile_hextalk` receives `source`, THE SYSTEM SHALL pass the whole `source` to `parseHexTalk` unchanged, with no white space trimmed and no line ending changed, so that every line and column refers to the text the chat sent.
2. IF `parseHexTalk` reports one or more errors, THEN THE SYSTEM SHALL return `ok` false as a normal result, not an error result, and SHALL return no canonical form. The result SHALL list the errors in the order `parseHexTalk` returns them, up to the cap of Requirement 5.6. Each error SHALL give its line and column exactly as `parseHexTalk` returns them (both 1-based, the column counted in UTF-16 code units) and the parser's message, unchanged except where Requirement 5.7 shortens quoted source text. The result SHALL also name every handler that compiled, in source order and spelled as on its `on` line. The list is empty when no handler compiled.
3. WHEN `parseHexTalk` reports no error, THE SYSTEM SHALL return `ok` true, the canonical form, which is exactly the text `printHexTalk(ast)` returns for the parsed AST, and the name of every handler, in source order and spelled as on its `on` line.
4. WHEN `compile_hextalk` receives as `source` a canonical form C that it returned for a source S, and C has at most 65,536 characters (the `source` limit of Requirement 5.3), THE SYSTEM SHALL return `ok` true, C itself as the canonical form, and the same handler names as for S. The AST that `parseHexTalk` returns for C SHALL deep-equal the AST it returns for S, ignoring `loc` (design spec §4.2, guarantee 2).
5. WHEN `parseHexTalk` reports no error and returns no handler (for example for an empty `source`, or one with only white space, blank lines and comments), THE SYSTEM SHALL return `ok` true, the empty string as the canonical form, an empty list of handler names, and the note `The script has no handlers.`
6. THE SYSTEM SHALL only parse and print the script and SHALL never run it. It SHALL send no message to the script's handlers and SHALL evaluate none of its statements. A script that would `wait`, `repeat forever`, `play`, `go` or `fetch` SHALL get the result of Requirements 7.2 to 7.5 like any other script.

### Requirement 8: conjure_script
**User Story:** As a Kiro chat, I want the same zero-config Spellcaster the studio uses, so that I can get a first draft of a script from English and see why a prompt was refused.

#### Acceptance Criteria
1. WHEN `conjure_script` receives a `prompt` and an optional `objectKind` that match its `inputSchema`, THE SYSTEM SHALL run the Tier 1 Spellcaster `conjureLocally(prompt, { objectKind })`, using `objectKind` `button` when the argument is omitted. The Spellcaster uses an exact Grimoire spell if there is one, else the local compiler, then the acceptance pipeline of design spec §4.4.
2. WHEN `conjureLocally` accepts the spell, THE SYSTEM SHALL return `ok` true and the HexTalk that `conjureLocally` printed from the accepted AST. `compile_hextalk` SHALL accept that HexTalk and return it unchanged as its canonical form. The result SHALL carry the note that `handlerHint(ast, objectKind)` gives for the accepted AST and the same object kind. It SHALL carry no note when `handlerHint` gives none. `handlerHint` gives a note only for a `button` or `field` spell that has a card-level handler such as `openCard` or `idle`.
3. IF `conjureLocally` refuses the prompt, including an empty or all-white-space prompt, THEN THE SYSTEM SHALL return `ok` false, as a normal result and not an error result. The result SHALL contain no HexTalk, the refusal reason exactly as `conjureLocally` gives it (apart from a quoted part of the prompt that Requirement 5.7 shortens), and the prompts of the 1 to 3 suggested Grimoire spells (`SUGGESTION_COUNT`) in the order `conjureLocally` returns them.
4. THE SYSTEM SHALL return, for every prompt of at most 600 characters and every object kind, the same HexTalk, note, refusal reason and suggested spells that the studio's Spellcaster tab shows for that prompt and object kind on an object whose script is empty. The only allowed difference is a part of the prompt quoted in a refusal reason that Requirement 5.7 shortens. A prompt of more than 600 characters gets the error result of Requirement 4.5, not the studio's "too long" refusal.
5. THE SYSTEM SHALL give `conjure_script` only two arguments: `prompt`, which is required, and `objectKind`, which is optional. No call can then choose a tier, a proxy or an API key. THE SYSTEM SHALL make the tool use only Tier 1. The tool SHALL make no network request and SHALL never run the conjured script.

### Requirement 9: render_card
**User Story:** As a Kiro chat building a stack, I want to see a card exactly as the studio draws it, and to get a text summary of it when I cannot see tool images, so that I can check and fix the layout without opening a browser.

#### Acceptance Criteria
1. WHEN `render_card` receives `stack`, THE SYSTEM SHALL read it and check it with the gate exactly as `validate_stack` does (Requirements 6.1 to 6.4), before it picks a card. IF `validate_stack` would return `ok` false for the same `stack` (a read error of Requirement 6.2 or the gate errors of Requirement 6.4), THEN THE SYSTEM SHALL return an error result whose `errors` list holds the same errors in the same order, at most 100 of them (Requirement 5.6), and that has no image content.
2. WHEN the gate accepts the stack, THE SYSTEM SHALL pick the card by `card`:
   - omitted: the first card of `cards`;
   - an integer n: the card at 1-based position n in `cards`;
   - a string: the card whose id equals the string exactly (case-sensitive). If there is none, the first card in `cards` order whose name equals the string after both are lower-cased with JavaScript's locale-independent `toLowerCase`, the comparison the VM uses for card names. A string is never read as a position, so `"2"` matches only an id or a name equal to `2`.
   IF no card matches (a position greater than the number of cards, or a string that is neither a card's id nor a card's name), THEN THE SYSTEM SHALL return an error result with no image content. The error SHALL state the number of cards and the selector, with the selector quoted as Requirement 5.7 states.
3. WHEN the card is picked, THE SYSTEM SHALL compose its frame from the stack exactly as given, with `composeFrame` and `createPartRasterizer` using the Node text backend (Requirement 10). The frame SHALL have no field being edited, no pressed part and no found text, and every `scrolling` field SHALL be at scroll offset 0. THE SYSTEM SHALL run no script, including `openStack` and `openCard` handlers, before or while it composes the frame. Hidden parts are left out and button icons from `customIcons` are drawn, as `composeFrame` and the part renderer do. This frame is the studio frame of the same stack in Browse mode with no field being edited, which Requirements 10.3 and 17.6 check.
4. WHEN the frame is composed, THE SYSTEM SHALL return a result that is not an error result. It SHALL have exactly two contents, in this order: a text content holding the result's JSON text with `ok` true, then one MCP image content (`image/png`). For `scale` k (1 or 2, default 1):
   - the PNG SHALL be 512k pixels wide and 342k pixels high;
   - the frame pixel at (x, y) SHALL fill the k x k block of image pixels from (kx, ky) to (kx + k - 1, ky + k - 1), using palette entry 0 for state 1 and palette entry 1 for state 2;
   - palette entry 0 SHALL be the colour of the stack's `lightBitHex` and entry 1 the colour of its `darkBitHex`, with the hex digits read case-insensitively;
   - the PNG SHALL be indexed colour with bit depth 1, a palette of exactly these two entries and no interlacing. It SHALL contain no chunk types other than `IHDR`, `PLTE`, `IDAT` and `IEND`, and a conforming PNG decoder SHALL read it without error.
5. WHEN the frame is composed, THE SYSTEM SHALL put in the result's JSON text a summary of the card, so that a chat that is not shown tool images still learns what the card holds. K1 does not say whether Kiro shows the chat model the image content of a tool result; the image check of the live import tests it (Requirement 16.1). The summary SHALL give:
   - the card's 1-based position in `cards`, the number of cards, the card's id and name, and its background's id and name;
   - the card size, 512 wide by 342 high, and the image size, 512k wide by 342k high for scale k;
   - the theme's `name`, and its `lightBitHex` and `darkBitHex` as the stack stores them, which are the two colours of the PNG palette;
   - the card's parts (Requirement 9.6);
   - the uncovered characters in the text of the card's visible parts, as Requirement 10.5 lists them: each character once per part, with the path of that part. A button's title counts only when `showName` is true. The list is empty when there are none.
   Every id, name, title and field text that the summary takes from the stack SHALL be quoted as Requirement 5.7 states.
6. WHEN the frame is composed, THE SYSTEM SHALL list every part in the summary in drawing order, hidden parts included: the background's parts, then the card's parts, each in array order. The list SHALL have at most 100 entries, followed by the number of parts not shown (Requirement 5.6). Each entry SHALL give:
   - the part's layer, type, id, name, rect and style;
   - whether the part is hidden (`visible` false, so it is not drawn), whether it is disabled (`enabled` false), and whether its rect extends beyond the card. A rect extends beyond the card exactly when `x` < 0, `y` < 0, `x + width` > 512 or `y + height` > 342;
   - for a button: its `title` only when `showName` is true, and its `iconId` only when it has one;
   - for a field: the text the field shows on this card, the length in characters of the full text, and the text's source. The source is one of three: the `content` of a card field; the shared `content` of a background field with `sharedText` true; or this card's `bgFieldContents` entry for a background field with `sharedText` false, where a missing entry gives empty text.
7. WHEN `render_card` is called twice with the same arguments, THE SYSTEM SHALL return byte-identical PNG data and identical JSON text. This SHALL hold within one server process and across two, and whether or not other tool calls come between the two calls.

### Requirement 10: Card Text in Node
**User Story:** As a Kiro chat, I want card text in a preview to match the studio pixel for pixel, or to be told exactly where it cannot, so that I can trust what `render_card` shows.

#### Acceptance Criteria
1. THE SYSTEM SHALL draw the text of `render_card` (button titles and field text) through `createPartRasterizer` and the text of `draw_layer` text commands through `renderCrisp1BitText`, with both functions unchanged, and SHALL pass the Node text backend to both. The Node text backend SHALL run in Node without a canvas, without `FontFace` and without native modules. It SHALL take every glyph outline and advance from the font file of the text's face, as `FONT_FILES` and `TEXT_SIZE_TABLE` select it, using the font bytes the server file carries (Requirement 3.1) and not by reading files.
2. THE SYSTEM SHALL make the Node text backend handle each code point of a text as follows (a surrogate pair is one code point):
   - U+0009, U+000B and U+000C: drawn and measured as U+0020 (space), whether or not the font maps them;
   - U+00AD and U+200B: nothing drawn and an advance of 0, whether or not the font maps them;
   - every other code point the font maps: its glyph, with an advance equal to the font's `hmtx` advance scaled to the face's render size (advance in font units x render size / `unitsPerEm`), without rounding;
   - an uncovered character: as Requirement 10.5 states.
   The backend SHALL measure a text as the exact sum of the advances of its code points, with no kerning. It SHALL draw each glyph at a pen position equal to the given `x` plus the advances of the code points before it.
3. WHEN `render_card` draws a card on which every text the part renderer draws (the title of every visible button with `showName` true, and the text every visible field shows on that card) consists only of covered characters of its face, and every paragraph of that text has fewer than 65,536 characters, THE SYSTEM SHALL return an image in which every pixel has the same colour as the pixel at the same position of the studio's card canvas. The canvas SHALL show the same card of the same stack, in Browse mode with the frame state of Requirement 9.3, in headless Chrome 157 on Linux (`--headless=new --disable-lcd-text`) after the bundled fonts have loaded. At scale 1 the image SHALL equal the canvas's 512 x 342 pixels. At scale 2 it SHALL equal a 1024 x 684 screenshot of the canvas at UI scale 2 and a device pixel ratio of 1. Requirement 17.6 checks this.
4. THE SYSTEM SHALL state, in the `render_card` description that `tools/list` returns and in the author-hexcard-stack skill, that the pixel match of Requirement 10.3 holds only for covered characters, that it was measured only in headless Chrome 157 on Linux, and that other browsers and operating systems were not checked.
5. IF the text that `render_card` draws for a part (Requirement 10.3), or the text of a `draw_layer` text command, contains an uncovered character, THEN THE SYSTEM SHALL draw the face's `.notdef` glyph, with the `.notdef` `hmtx` advance, in place of every occurrence. It SHALL list each distinct uncovered character once per part or command, in order of first occurrence. Each entry SHALL give the character as `U+` followed by at least four uppercase hexadecimal digits of its code point (an unpaired surrogate counts as the code point of its own code unit), together with the path of the part in the path format of `validateStack` (for example `backgrounds[0].parts[2]`) or the path of the command (for example `commands[2]`). For each listed part, THE SYSTEM SHALL also state that the studio draws the character with a system fallback font, so the studio's pixels of that part can differ from the preview.
6. THE SYSTEM SHALL cover printable ASCII (U+0020 to U+007E) in every face: every font file the server carries SHALL map all 95 of these code points, and a test SHALL fail if any of them is unmapped.

### Requirement 11: draw_layer
**User Story:** As a Kiro chat building a stack, I want to describe simple 1-bit art as a short list of drawing commands and get canonical rleData back, so that cards and backgrounds can have pictures without hand-written bitmap data.

#### Acceptance Criteria
1. WHEN `draw_layer` receives `layer` and `commands` that pass every limit of Requirement 5.3, THE SYSTEM SHALL start from the base of the layer kind (every pixel 0, transparent, for `card`; every pixel 1, light, for `background`) and SHALL draw the commands in list order. A command SHALL change only the pixels it sets. A pixel that a later command sets SHALL take that command's state, whatever an earlier command set it to.
2. WHEN a command is a rectangle (`op` `rect`, with `x`, `y`, `width`, `height`, an optional `pattern` with default 1 and an optional `filled` with default false), THE SYSTEM SHALL set the pixels that the studio's Rect tool sets for a drag from (`x`, `y`) to (`x + width - 1`, `y + height - 1`) with that pattern and with the Rect tool's filled setting equal to `filled`. When `filled` is false, these are the pixels of the 1-pixel frame of the box: columns `x` and `x + width - 1` and rows `y` and `y + height - 1`, within the box. When `filled` is true, they are every pixel of the box. Each pixel SHALL take the state that `patternState` gives for the pattern at the pixel's own layer coordinates (spec 03 Requirement 7.2), so pattern index 0 sets state 1 (light) and pattern index 1 sets state 2 (dark).
3. WHEN a command is a line (`op` `line`, with `x1`, `y1`, `x2`, `y2` and an optional `pattern` with default 1), THE SYSTEM SHALL set the pixels that the studio's Line tool sets for a drag from (`x1`, `y1`) to (`x2`, `y2`), in that direction. These are the pixels that `bresenhamLine(x1, y1, x2, y2, …)` visits, both ends included, each in the state that `patternState` gives for the pattern at the pixel's own layer coordinates. Swapping the two ends can set different pixels, so the order of the points is part of the command.
4. WHEN a command is a sprite (`op` `sprite`, with `x`, `y` and `rows`), THE SYSTEM SHALL set the pixel at (`x + column`, `y + row`) to state 2 (dark) for every `#` and to state 1 (light) for every `.` at `rows[row][column]`, with `row` and `column` counted from 0.
5. WHEN a command is a text (`op` `text`, with `x`, `y` and `text`, and the optional `width` with default `512 - x`, `height` with default `342 - y`, `font` with default `Sans`, `size` with default 12, `style` with default an empty list, `align` with default `left`, `wrap` with default true and `ink` with default `dark`), THE SYSTEM SHALL lay out and draw `text` with `renderCrisp1BitText` and the Node text backend, in the face that `TEXT_SIZE_TABLE` selects for `font`, `size` and whether `style` holds `bold`. The text SHALL be drawn in the box (`x`, `y`, `width`, `height`) with no inset. With `wrap` true, lines SHALL wrap as they do in a field whose `dontWrap` is false. With `wrap` false, lines SHALL break only at line breaks, as they do in a field whose `dontWrap` is true. THE SYSTEM SHALL set every ink pixel of the returned mask to state 2 for `ink` `dark` or to state 1 for `ink` `light`, and SHALL leave the other pixels unchanged. The allowed values are those of a field: `font` is `System`, `Sans`, `Mono` or `Serif`; `size` is 9, 10, 12, 14, 18 or 24; `style` lists each of `bold`, `italic`, `underline`, `outline`, `shadow` and `condense` at most once; `align` is `left`, `center` or `right`; `ink` is `dark` or `light`. The defaults are the text settings of a new field.
6. THE SYSTEM SHALL export the Rect tool's drawing, which today is internal to `createPaintController`, from `paintTools.ts` as one function, and both the Rect tool and `draw_layer` SHALL draw rectangles by calling that function. THE SYSTEM SHALL draw lines with `bresenhamLine`, take patterns from `PATTERNS` and take pattern states from `patternState`, the code the studio's Line and Rect tools use. The paint tools SHALL keep setting the same pixels for every drag, pattern and filled setting (Requirement 14.2).
7. WHEN `draw_layer` has drawn every command and the drawn pixels differ from the base in at least one pixel, THE SYSTEM SHALL return `ok` true, the layer kind, the `rleData` that `encodeBitmapRLE` produces from the drawn pixels, and two counts taken over all 175,104 pixels of the drawn layer, base pixels included: the number of pixels in state 1 (light) and the number in state 2 (dark). This `rleData` SHALL be canonical, and `decodeBitmapRLE` SHALL turn it back into exactly the drawn pixels.
8. IF the drawn pixels equal the base in every pixel (for example a `background` layer on which every command set only light pixels, or a `card` layer whose only command is a text of spaces), THEN THE SYSTEM SHALL return `ok` true, the layer kind, `rleData` `""` (the canonical empty layer, which `decodeBitmapRLE` turns into the base of the layer kind) and the two pixel counts of Requirement 11.7.
9. IF a line of a text command does not fit in the command's box, THEN THE SYSTEM SHALL drop that line's pixels outside the box and SHALL add one note for the command that names its path (for example `commands[2]`) and the number of its lines that do not fit, without changing `ok`. Lines lie one line height of the face apart (`lineMetrics`), the first with its top at `y`. A line does not fit when its drawn width, styles included, is at least 1 and either the drawn width is greater than `width` or the line's top plus the line height is greater than `y + height`. A line whose drawn width is 0 (empty or only spaces) always fits. Uncovered characters in a text are drawn and listed as Requirement 10.5 states, without changing `ok`.
10. IF a drawing command or the call breaks a limit of Requirement 5.3, including the rules that the `inputSchema` cannot express (a point or shape outside the layer, sprite rows of different lengths, a sprite character other than `#` and `.`, more than 65,536 characters of sprite rows and texts), THEN THE SYSTEM SHALL answer with an error result whose `errors` list holds one entry for every broken rule, with the path of the argument that breaks it (for example `commands[3].rows[1]`). The list SHALL follow command order, with the limit on the call's total characters last, and SHALL be shortened as Requirement 5.6 states. THE SYSTEM SHALL draw nothing and SHALL return no `rleData`.
11. WHEN `draw_layer` is called twice with the same arguments, THE SYSTEM SHALL return the same JSON text both times, for a result and for an error result.

THE SYSTEM SHALL fail a test in `npx vitest --run` when that block differs from design spec §4.1.
3. THE SYSTEM SHALL make the skill state these rules of design spec §3, §3.2, §4.1, §4.2 and §4.3, with the numbers given here:
   - the step budget: 10,000 steps per top-level dispatch, shared with its nested dispatches. Every evaluated statement and expression costs 1 step, and every loop iteration costs 1 more. Running out stops the whole dispatch with the script error "Loop exceeded 10,000 steps" and keeps every change made before that point;
   - nested dispatches: `go` sends `closeCard` and `openCard` (and `closeBackground` and `openBackground` when the background changes) as nested dispatches inside the running one. Nesting deeper than 16 levels stops the dispatch with the script error "Too much recursion";

On failure the destination stays unchanged and `it` becomes `error: <reason>`, with the reasons that §4.3 lists;
   - variables: a variable is local to the running handler. `get`, `answer`, `ask` and `fetch` write `it`, and an unset variable reads as empty. `global x` makes `x` a runtime-wide global for the rest of the handler. Globals are kept in memory only and are never saved or exported;
   - the message path: the target part (a button, or a field with `lockText` true), then the card, the background, the stack and the built-in handlers. The first object with a handler for the message handles it. `pass <message>` ends the handler at once and sends the same message with the same parameters to the next object on the path. Mouse messages go to the part under the pointer, or to the card when no part is hit. An unlocked field gets no mouse messages in Browse mode. `idle` and lifecycle messages start at the card.

   - `exit` naming a handler other than the enclosing one;
   - `else if` on one line;
   - a one-line `if ... then ... else`;
   - a `"` inside a string literal, fixed with `quote`;
   - `send`;
   - `do`;
   - a user-defined function;
   - a chunk expression such as `word 2 of`;
   - a reserved word used as a variable name;
   - a second handler with the same name.
   THE SYSTEM SHALL also make the skill explain that `field N` without a layer word means a background field and that `button N` without a layer word means a card button. This case gives no compile error. The explanation SHALL include a HexTalk example that uses both references without a layer word, followed by the canonical form that `compile_hextalk` returns for it, which shows the layer word of each reference.
5. THE SYSTEM SHALL make the skill explain how to check a script with `compile_hextalk`:

   - read each error's 1-based line and column, counted from the start of the script;
   - fix the script and call `compile_hextalk` again until it returns `ok` true. The parser reports only the first error of each handler and skips to that handler's `end` line (spec 02 Requirement 1.2), so one fix can reveal the next error in the same handler;
   - store the returned canonical form as the `scriptSource`, not the text that was sent. The canonical form can differ from the sent text in synonyms, `if` blocks, layer words and indentation (design spec §4.2);
   - `ok` true with the note that the script has no handlers means that the script responds to no message;
   - `validate_stack` reports the same errors for a stored script, written `<path> line L, column C: <message>` with the path of its `scriptSource` as `<path>`.

   - `objectKind` is one of `button`, `field`, `card`, `background` and `stack` (default `button`). It must be the kind of object that will hold the script, because it picks the handler used when the prompt names no message, and the object that `me` names;
   - the `handlerHint` note means that the handler never runs in that kind of object;
   - a refusal gives a reason and the prompts of suggested Grimoire spells;
   - the returned HexTalk is a draft. The chat reads it and checks it with `compile_hextalk`, like any other script, before storing it.
6. THE SYSTEM SHALL make the skill say that a script enters a stack only as the `scriptSource` string of the stack, a background, a card or a part. The skill SHALL say that this string is written as a JSON string (each line break as `\n`, each `"` as `\"`), and never as an AST or under any other key, and that `validate_stack` rejects an object with an unknown key.
